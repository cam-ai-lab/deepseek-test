# Preface

You already know that tests are good. You have probably written plenty of them — maybe years ago,
maybe in a different language, maybe back when "the integration environment" was a server under
somebody's desk. What has changed since then is not the *idea* of testing. It is the vocabulary,
the tooling, and above all the number of ways a modern team slices its tests: unit, slice,
integration, contract, component, system, end to end, black-box, acceptance, smoke, regression,
ephemeral, synthetic… Every team uses a different subset of those words, and uses them to mean
slightly different things.

This book has one goal: to get you from *"I get the ideas"* back to *"I can design, write and
defend a test suite, and I can tell every style of test apart."* We will do that the only way that
reliably works — by building things.

## Who this book is for

You are an engineer, tech lead, architect or engineering manager who:

- understands what a unit test is, but hasn't been hands-on with a modern Java stack for a while;
- hears terms like *slice test*, *Testcontainers*, *consumer-driven contract* or *ephemeral
  environment* and wants to know precisely what they mean and when they matter;
- wants to make decisions about a team's test strategy and be able to explain *why*.

You don't need to be a Spring expert. You do need to be comfortable reading Java.

## The lab: a small service with a real test suite

Throughout the book we work on one small application: **the quote service**. It prices loans. A
client sends a command — *"quote me 10,000 USD over 12 months for product WIDGET"* — and the service
asks another team's **rate service** for the annual interest rate, calculates the total, stores the
quote in PostgreSQL and returns it.

It is deliberately small, about 400 lines of production code, so you can hold all of it in your
head. But its test suite is not a toy. It has three tiers, build-enforced rules about which tests
may use which libraries, a guard that watches how many Spring contexts the suite boots, real
PostgreSQL in containers, and a golden-file contract test. In Part 3 we go further and add a proper
black-box suite written in Cucumber.

The service was generated by an AI model and then reviewed. That turns out to be a gift for a
testing book: the code is clean and idiomatic, and it *still* has bugs that its own tests cannot
see. Finding out why those tests are blind — and building tests that aren't — is the spine of this
book.

## How this book is organised

The book has four parts.

- **Part 1, A map before the territory**, gives you vocabulary. Chapter 2 introduces the
  *four axes of testing*, the framework the rest of the book hangs on.
- **Part 2, Testing inside the box**, covers everything that runs inside or next to the
  application's JVM: unit tests, golden files, architecture rules, Spring slices, real databases,
  adapter tests and the build machinery that holds a test suite together.
- **Part 3, Testing from the outside**, is about black-box testing: what it really means, why the
  lab's current "system tests" don't qualify, and how to build a Cucumber suite that tests the real
  Docker image.
- **Part 4, Phases, environments and pipelines**, zooms out: where tests run, performance testing,
  CI design, and how to choose a strategy for a real team.

Read Parts 1 and 2 in order. After that, chapters are more independent.

## How each chapter works (and why)

Research on how adults learn technical material is remarkably consistent about a few things, and
this book leans on them deliberately:

- **Retrieval beats re-reading.** Trying to recall something — even failing to — strengthens memory
  far more than reading it again. So every chapter after the first opens with a short **Warm-up**
  asking you to recall ideas from earlier chapters, and closes with a **Check your understanding**
  quiz. Answers to the quizzes are in appendix B. Resist the urge to peek; the struggle is the
  point.
- **Words plus pictures.** Every important idea comes with a diagram. They are drawn in high
  contrast and never rely on colour, so they read fine on an e-ink screen or a phone.
- **Worked examples first, then fade.** We start with fully worked code from the lab, move to
  partly worked examples where you fill in a gap, and end with exercises you do on your own.
- **Name the misconceptions.** Many testing mistakes come from beliefs that sound right. Each one
  gets called out explicitly, with the reason it's wrong.
- **Interleave.** Later chapters deliberately mix earlier concepts back in, so you keep practising
  *telling them apart* — which is the skill that separates a testing expert from someone who has
  memorised definitions.

## About the code

The lab lives in a Git repository, and the book follows its history. Parts 1 and 2 study the suite
as it was *before* the black-box migration; that state is tagged `before-blackbox`:

```
quotes/  (git checkout before-blackbox)
├── build.gradle.kts       # the build, including the test tiers
├── compose.yaml           # local PostgreSQL for development
├── src/main/              # the application
├── src/test/              # UNIT tier
├── src/integrationTest/   # INTEGRATION tier
├── src/systemTest/        # SYSTEM tier (in-JVM, grey-box)
└── src/testFixtures/      # shared test helpers
```

Parts 3 and 4 follow the migration that replaced the system tier with a black-box suite. On the
`main` branch you'll find the result:

```
quotes/  (main)
├── Dockerfile             # the image the black-box suite tests
├── compose.blackbox.yaml  # app + PostgreSQL + WireMock, for the suite
├── docker/postgres-init/  # the read-only role for assertions
├── blackbox/              # BLACK-BOX tier: Cucumber, plus the Gatling smoke test
├── src/test/              # UNIT tier
├── src/integrationTest/   # INTEGRATION tier
└── src/testFixtures/      # shared test helpers
```

Listings are taken from the repository — from `before-blackbox` in Parts 1 and 2, from `main` in
Parts 3 and 4 — abridged where noted. Where the implementation deviated from the original plan, the
chapter says so and explains why; those deviations are some of the most instructive parts of the
book. Appendix A tells you how to set up a machine to run everything.

Let's begin with a question that sounds naive and isn't: what are tests actually *for*?
